¿Qué es y para qué sirve?

El conector Cassandra permite que el agente de Ruvic consulte tu clúster Apache Cassandra en modo solo lectura: puede explorar y leer datos, pero nunca modificarlos. Una vez configurado, puedes pedirle al agente cosas como:

  • "Lista los keyspaces y tablas del clúster de Cassandra."
  • "Muéstrame las últimas 50 filas de la tabla pedidos del keyspace ventas."
  • "¿Cuántos pedidos tiene el cliente ACME? Ejecuta un SELECT para averiguarlo."

Operaciones soportadas:

Operación Qué hace
db.list_keyspaces_and_tables Lista los keyspaces del clúster y las tablas de cada uno (excluye keyspaces internos del sistema por defecto)
db.read_rows Lee filas de una tabla con un límite (default 100, máximo 1000)
db.execute_cql Ejecuta una sentencia CQL de solo lectura (SELECT); cualquier otra sentencia se rechaza antes de llegar a Cassandra
Solo lectura, por diseño El conector valida a nivel de código que toda sentencia CQL empiece con SELECT; INSERT, UPDATE, DELETE, CREATE, DROP, ALTER y TRUNCATE se rechazan antes de ejecutarse, sin importar el rol otorgado al usuario en Cassandra.

Prerrequisitos

  • Un clúster Apache Cassandra (autoalojado, en la nube o en Docker) con autenticación habilitada (PasswordAuthenticator).
  • Acceso administrativo al clúster (usuario con permiso para crear roles vía cqlsh), solo durante la configuración inicial.
  • Acceso de red desde la plataforma Ruvic al clúster (nodos de contacto y puerto alcanzables; regla de firewall o security group si aplica).
  • Los datos de conexión: nodos de contacto (hosts), puerto (por defecto 9042) y el nombre del datacenter local (ver nodetool status).

Configuración en el fabricante

Vas a crear un rol dedicado de solo lectura para Ruvic. No reutilices el rol cassandra ni un rol de aplicación: un rol dedicado permite auditar la actividad del agente y limitar el acceso al mínimo.

  1. Conéctate al clúster como administrador. Usa cqlsh con un rol administrador (por ejemplo el rol superuser inicial cassandra/cassandra): 
    cqlsh TU_HOST 9042 -u cassandra -p CONTRASEÑA_ADMIN
  2. Crea el rol de solo lectura para Ruvic. Elige una contraseña fuerte (mínimo 16 caracteres, generada aleatoriamente) y guárdala: la usarás en el formulario de Ruvic (campo Contraseña). 
    CREATE ROLE ruvic_reader WITH PASSWORD = 'CAMBIA_ESTA_CONTRASEÑA' AND LOGIN = true;
  3. Otorga permiso SELECT sobre los keyspaces a exponer. Otorga sobre keyspaces específicos en vez de todo el clúster cuando sea posible (repite para cada keyspace que el agente deba consultar): 
    GRANT SELECT ON KEYSPACE ventas TO ruvic_reader;
    Nota Listar keyspaces y tablas (db.list_keyspaces_and_tables) usa las tablas del sistema system_schema, legibles por cualquier rol autenticado; no necesitas un GRANT adicional para esa operación.
  4. Habilita el acceso de red desde Ruvic. Si tu clúster restringe conexiones por IP (habitual en producción), permite la IP de la plataforma Ruvic:
    • Servidor propio: abre el puerto 9042 (o el configurado) en el firewall del nodo hacia la IP de Ruvic.
    • Cloud gestionado (Astra DB, AWS/GCP/Azure): agrega la IP en el security group, la lista de acceso o el allowlist del proveedor.
    [ Captura: regla de firewall / security group con la IP de Ruvic — reemplazar por assets/img/cassandra-firewall.png ]
  5. Verifica el rol desde fuera del servidor. Desde una máquina distinta al nodo de Cassandra (idealmente con salida de red similar a la de Ruvic): 
    cqlsh TU_HOST 9042 -u ruvic_reader -p TU_CONTRASEÑA -e "SELECT release_version FROM system.local"

    Si responde con la versión del clúster, el fabricante quedó listo. Anota estos valores para la siguiente sección: hosts, puerto, usuario, contraseña y datacenter local.

Permisos requeridos

Principio de mínimo privilegio: el rol de Ruvic solo necesita SELECT sobre los keyspaces a consultar. No otorgues permisos de escritura (MODIFY) ni de administración (CREATE, ALTER, DROP, AUTHORIZE).

Permiso Para qué sirve
LOGIN Permite que el rol se autentique en el clúster
SELECT (por keyspace) Leer filas de tablas (db.read_rows) y ejecutar CQL de lectura (db.execute_cql) sobre los keyspaces expuestos
Lectura de system_schema Listar keyspaces y tablas (db.list_keyspaces_and_tables); disponible para cualquier rol autenticado sin GRANT adicional

No se requieren permisos de escritura (MODIFY) ni de administración (CREATE, ALTER, DROP, AUTHORIZE). El conector rechaza a nivel de código cualquier sentencia CQL que no empiece con SELECT, aunque el rol otorgado tuviera esos permisos.

Configuración en Ruvic

Entra a Settings → Conectores, busca la tarjeta Cassandra y pulsa Configurar. Diligencia el formulario (modo de autenticación "Usuario y contraseña") con los valores que obtuviste en la sección anterior:

Campo del formulario Valor
Hosts (contact points) Uno o más nodos de contacto separados por coma (ej. 10.0.0.1,10.0.0.2)
Puerto 9042 (salvo configuración distinta)
Usuario ruvic_reader
Contraseña La contraseña del paso 2. Se guarda cifrada como secreto: la interfaz no volverá a mostrarla
Datacenter local Nombre exacto del datacenter local (ej. datacenter1), requerido por el driver — consulta nodetool status si no lo conoces
Timeout de conexión Opcional; 10 segundos por defecto

Probar conexión — la plataforma se conectará al clúster y confirmará que las credenciales, el datacenter y la red funcionan.

Verificación

  1. Test de conexión exitoso.

    El botón Probar conexión ejecuta test_connection(), que hace ping al clúster con SELECT release_version FROM system.local. Debe responder: "Conexión exitosa a Cassandra [hosts]". La tarjeta del conector cambia a estado Configurado.

  2. Automatización mínima de prueba.

    Abre una conversación nueva con el agente y pídele:

    "Lista los keyspaces y tablas del clúster de Cassandra."

    El agente debe responder con el listado real de tus keyspaces y tablas (usando db.list_keyspaces_and_tables). Si lo hace, el conector quedó operativo de punta a punta.

Solución de problemas

Mensaje / síntoma Causa probable y solución
"Autenticación fallida: Credenciales inválidas o sin permiso suficiente sobre el clúster." Usuario o contraseña incorrectos, o el rol no tiene LOGIN habilitado. Verifica el rol con cqlsh (paso 5 de "Configuración en el fabricante") y vuelve a guardar el formulario con la contraseña correcta.
"No se pudo alcanzar ningún nodo de [hosts]. Revisa host/puerto/red y el datacenter local configurado." / "Timeout al conectar con el clúster Cassandra." La plataforma no alcanza los nodos de contacto. Revisa el firewall/security group (paso 4), que el host no sea localhost (debe ser accesible desde Ruvic, no desde tu equipo) y que el puerto 9042 esté abierto.
El agente lista tablas pero falla al leer una con "Error de datos" / permiso denegado Falta el GRANT SELECT sobre ese keyspace. Repite el paso 3 de "Configuración en el fabricante" para el keyspace correspondiente.
"El datacenter local configurado no coincide" o errores de DCAwareRoundRobinPolicy El campo "Datacenter local" no coincide con el nombre real del clúster. Ejecuta nodetool status en un nodo y usa exactamente el nombre que aparece ahí, incluso si el clúster tiene un solo datacenter.
El conector aparece "Sin configurar" tras guardar Algún campo obligatorio quedó vacío. Ábrelo de nuevo y completa hosts, puerto, usuario, contraseña y datacenter local (todos obligatorios salvo timeout).

Preguntas frecuentes y notas de seguridad

¿El agente puede modificar o borrar datos?

No. El conector valida en código que toda sentencia CQL empiece con SELECT (INSERT, UPDATE, DELETE, CREATE, DROP, ALTER y TRUNCATE se rechazan antes de llegar a Cassandra), y el rol ruvic_reader solo tiene permiso SELECT. Son dos barreras independientes.

¿Dónde queda guardada la contraseña?

Como secreto en el almacén de credenciales de la plataforma, asociado a tu usuario. La interfaz nunca vuelve a mostrarla; solo indica "definida". Para cambiarla, escribe una nueva en el formulario; para conservarla al editar otros campos, deja el campo vacío. El código del agente nunca hardcodea la contraseña: siempre se lee de la variable de entorno RUVIC_CASSANDRA_PASSWORD.

Rotación de credenciales

Recomendado cada 90 días o según tu política: cambia la contraseña en Cassandra (ALTER ROLE ruvic_reader WITH PASSWORD = '...'), actualízala en el formulario del conector y pulsa Probar conexión.

¿Qué hago si la contraseña se compromete?

  1. Cambia la contraseña en Cassandra de inmediato (ALTER ROLE ruvic_reader WITH PASSWORD = '...') o desactiva el rol (ALTER ROLE ruvic_reader WITH LOGIN = false).
  2. Revisa la actividad reciente del rol en los logs de auditoría del clúster (si están habilitados).
  3. Actualiza la nueva contraseña en el formulario del conector.

¿Por qué el mínimo privilegio importa tanto en un conector de solo lectura?

Aunque el código bloquea escrituras, otorgar SELECT solo sobre los keyspaces que el agente realmente necesita limita qué datos puede ver si las credenciales se filtran. Evita otorgar SELECT sobre todo el clúster cuando baste con uno o dos keyspaces.

Buenas prácticas Usa siempre un rol dedicado y de solo lectura (nunca el rol cassandra ni uno de aplicación); restringe el acceso de red por IP; otorga SELECT solo sobre los keyspaces que el agente necesita; y evita compartir la contraseña por canales no seguros.
